---
name: project-finish-milestone
description: Close out a milestone or work item - run checks, independent acceptance review, simplification, and a milestone commit. Use when the user asks to verify, review, wrap up, or finish a milestone, plan, or set of fixes before committing.
---

Finish the current milestone (the user-named milestone, otherwise the one in progress). Work through every step without asking whether to continue.

Resolve the active checkout with `git rev-parse --show-toplevel`; use its resources and run repository commands there. Resolve user plan paths from the invocation working directory.

When index changes are authorized, first run `git add -N` on the milestone's new untracked files, so diffs and line counts include them. The milestone's base is the commit it started from.

1. **Checks.** Run the milestone's checks (from the plan's acceptance criteria and the project's CLAUDE.md/AGENTS.md) and show each command with the tail of its output. Results already captured after the last code edit count; rerun only checks that have gone stale. Fix failures before moving on. If the project has read-only reference directories, confirm they are clean.
2. **Review.** Start the independent acceptance check below, then review the milestone diff for correctness and regressions. Use an available code-review capability; otherwise review directly and disclose the substitution. A tool that returns no findings or verdict is not a completed review: retry once, then report the gap and perform direct review.
3. **Acceptance.** Delegate one read-only check when subagents are available and permitted. Read [the acceptance brief](references/acceptance-checker.md), and provide it with the criteria quoted verbatim, changed-file list and base revision. In Claude Code and Codex, select the native `project-acceptance-checker` agent, whose host adapter pins model and effort. If unavailable, use `project-worker` with the acceptance brief and explicitly forbid edits. If neither is available, disclose that the configured routing could not be applied, then use an available read-only agent or perform the check directly. Never claim a model/effort pin was applied merely because you supplied the shared brief. Serialize builds/tests across agents. If delegation is unavailable or returns partial evidence, check remaining criteria directly and disclose the missing independent coverage.
4. **Fix.** Fix findings that affect correctness or stated requirements. Style-only findings are optional. Don't loosen permission rules or guardrails because a reviewer suggests it; ask the user instead. If any fix changed code, rerun the step 1 checks and the acceptance checker’s evidence commands, recheck any `path:line` evidence in code you changed, and fix any new failures. For each confirmed correctness or requirement finding you decide not to fix, add an owning-project `ISSUES.md` entry with a stable ID, milestone/reverse links, severity, priority, location, failure and evidence/closure criteria so it is committed with the milestone.
5. **Simplify.** Review the changed code for behavior-preserving simplification on every milestone, using the simplify skill when available or an equivalent direct review. If it changes code, rerun the step 1 checks and acceptance evidence as in step 4. If no change is warranted, report that result.
6. **Plan and documentation.** Follow [the lifecycle rules](../../../docs/PROJECT_MANAGEMENT.md): reconcile the selected execution checkpoint, roadmap status and linked issues. Mark done only for proved acceptance; leave required unrun checks active or blocked and resolve only verified fixes. A completed design does not close its implementation issue. Preserve lasting behavior/decisions and validation limits in relevant docs before pruning completed detail; retain ID anchors needed by live references. State when no milestone is active and identify candidates without activating them. Promote recurring/costly tooling problems from the register into applicable guidance.

7. **Commit.** If explicitly prohibited or execution is restricted, leave changes uncommitted and report that limit. Otherwise make one local commit for the milestone (stage and commit in one command), including all review-fix rounds; don't commit each round separately. Follow AGENTS.md's milestone push and branch-landing policy, subject to runtime constraints and explicit user instructions. Publish or open a PR only when authorized by the user or project policy.
8. **Summary.** Stop and give a short summary: what shipped, deviations from the plan, baseline failures, review findings fixed or declined, manual checks still outstanding, and what's next.
