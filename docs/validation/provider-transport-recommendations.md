# Gmail and Microsoft 365 transport recommendations: P2

Reviewed **2026-10-13, America/Vancouver** against base `d579059bd5af1ca898c619b5abd02f4923139643`, branch `docs/provider-deliverability-review`. This research completes the [P1 audit](provider-deliverability-review.md); its code findings and PD1–PD9 in `ISSUES.md` remain unfixed. No application code, credentials, registrations, dependencies, tenant policy or DNS changed. Recommendations are engineering judgments, not live compatibility results. Implementation awaits the user's architecture choice.

## Recommendation and decision boundary

**Gmail: retain and harden IMAP/SMTP.** It reuses Mailven's receiving, MIME and encryption paths with the least migration risk. API submission offers structured errors and a sent-message resource, but retaining IMAP retains its broad OAuth scope and Workspace IMAP policy dependency. There is no evidence that changing submission alone improves inbox placement. Choose full Gmail API instead only if Workspace IMAP restrictions or label-native synchronization justify a separate backend; restricted mail-data scopes and admin approval still apply. [Gmail XOAUTH2](https://developers.google.com/workspace/gmail/imap/xoauth2-protocol), [API scopes](https://developers.google.com/workspace/gmail/api/auth/scopes)

**Microsoft 365: target full delegated Graph mail integration.** This removes both IMAP and SMTP AUTH dependencies and better fits tenants that restrict those protocols. It costs substantially more than send-only Graph, requiring receiving, folder operations, offline replay and shared-mailbox parity. Existing IMAP/SMTP remains an explicit compatibility route where permitted; do not silently switch existing accounts. A Graph-send/IMAP-receive hybrid is an optional intermediate release only for tenants permitting IMAP. It cannot serve a tenant that disables IMAP. Security defaults can disable SMTP AUTH; Graph access still depends on consent and organizational policy. [SMTP AUTH controls](https://learn.microsoft.com/en-us/exchange/clients-and-mobile-in-exchange-online/authenticated-client-smtp-submission), [Graph permissions](https://learn.microsoft.com/en-us/graph/permissions-reference)

Outlook.com is a separate compatibility target, not proof of Microsoft 365 tenant behavior. Graph delegated Mail.Send supports personal Microsoft accounts; shared/delegated organizational scenarios require separate testing. Keep user-supplied desktop OAuth credentials and registered account audience. Do not introduce application-only tenant-wide access or require users to weaken security defaults. [Graph sendMail](https://learn.microsoft.com/en-us/graph/api/user-sendmail?view=graph-rest-1.0)

Send-as settings include verification status and optional external SMTP configuration; they do not prove recipient-side authentication. Gmail sync history can expire with HTTP 404, requiring full synchronization. These are API requirements; effort and migration assessments are judgments based on P1's existing IMAP implementation.

Gmail API adds per-project and per-user quota-unit budgets, separate from sending allowances. Sending quotas are shared across the user's clients; documented quota enforcement can lag, so even a successful HTTP response is not proof of successful sending or delivery. Respect provider retry timing/backoff for definite throttling; preserve an unknown outcome after a possibly processed send request instead of blindly replaying it. [API usage limits](https://developers.google.com/workspace/gmail/api/reference/quota), [API errors and sending limits](https://developers.google.com/workspace/gmail/api/guides/handle-errors)

Sources: [protocol OAuth scopes](https://learn.microsoft.com/en-us/exchange/client-developer/legacy-protocols/how-to-authenticate-an-imap-pop-smtp-application-by-using-oauth), [Graph permission definitions](https://learn.microsoft.com/en-us/graph/permissions-reference), [per-folder delta](https://learn.microsoft.com/en-us/graph/delta-query-messages), [message resource and Bcc](https://learn.microsoft.com/en-us/graph/api/resources/message?view=graph-rest-1.0), [MIME/sendMail](https://learn.microsoft.com/en-us/graph/api/user-sendmail?view=graph-rest-1.0), [Graph throttling](https://learn.microsoft.com/en-us/graph/throttling), [resource-specific token acquisition](https://learn.microsoft.com/en-us/entra/identity-platform/msal-acquire-cache-tokens), [raw MIME retrieval](https://learn.microsoft.com/en-us/graph/outlook-get-mime-message).

Shared submission needs both delegated Graph and Exchange mailbox permissions. Send As and Send on Behalf differ in visible identity. `/me` normally saves in the signed-in user's Sent; sending via the From mailbox normally saves there and additionally requires Full Access. Administrator copy settings can add another copy even when the request disables saving. Treat these as policy, not a generic single-Sent guarantee. [Sending from another user](https://learn.microsoft.com/en-us/graph/outlook-send-mail-from-other-user)

Graph `202 Accepted` means the request was accepted, **not completed processing, delivery or inbox placement**. Record provider acceptance separately from later bounce/observed delivery; a lost HTTP response can still leave submission uncertain. [sendMail response](https://learn.microsoft.com/en-us/graph/api/user-sendmail?view=graph-rest-1.0)

Large Graph attachments can require draft/upload-session operations and Mail.ReadWrite rather than Mail.Send alone. The documented upload path supports files up to 150 MB, but mailbox message limits still apply and the page flags a shared/delegated-mailbox issue. Do not turn that maximum into a UI sending promise or rebuild encrypted MIME as separate plaintext attachments. Select a validated size strategy or report a clear unsupported case before submission. [Large attachments](https://learn.microsoft.com/en-us/graph/outlook-large-attachments)

## Common hardening before transport changes

P1's existing code is the baseline: `internal/smtp/message.go:105–135` omits Bcc from wire headers, `internal/smtp/client.go:351–394` submits envelope recipients and reports generic DATA errors, and `app/compose.go:464–509` applies the SMTP route and host-based Sent policy. API sending is not an existing feature to enable. Apply the following to every retained/new route:

- PD1/PD2: correct setup and refresh guidance; distinguish Outlook.com and tenant endpoints. Validate existing accounts before any endpoint migration.
- PD3: durable submission states for not submitted, definite rejection, provider accepted and unknown outcome; user review before resubmitting unknown mail. Keep Sent/cleanup failure separate from submission failure.
- PD4/PD6/PD8: validate header physical/value limits, final encoded/encrypted size, recipients and international envelope capability before network submission. Preserve content; explain unsupported cases.
- PD5/PD9: record actual granted scopes/capabilities, distinguish authorized, known-unverified and unknown identity evidence. Never label lookup failure as permission success.
- PD7 and U3: explicit Sent policy per route/mailbox, linked-account refresh/revocation tests and stable reconciliation identifiers. Migration must preserve drafts, queued mail, account IDs and encrypted credential storage.

API-specific work is separate: resource-correct OAuth tokens, recipient-bearing submission representation, response/backoff adapters, API Sent reconciliation, and eventually API receiving/cache migration. Provider relay reputation, signing and recipient filtering remain external; no approach promises better inbox placement. See P1's responsibility matrix and [Gmail sender guidance](https://support.google.com/mail/answer/81126?hl=en).

## Proposed user-invoked account diagnostic

Add **Check account setup** to account settings. The user chooses the account, From identity and intended route, then starts or cancels the check. No background run, automatic test email, DNS change, delivery score or send endpoint call. Authenticated read/connection probes may refresh credentials through the existing secure flow; do not initiate new consent without an explicit reauthorization action.

| Check | Evidence and result | Actionable guidance / limits |
| --- | --- | --- |
| Transport / authentication | Effective endpoints, TLS/certificate result, OAuth resource, expiry and actual granted scopes; bounded IMAP login/capability and SMTP EHLO/auth probes without MAIL/RCPT/DATA. API routes use a minimal authorized read only when granted; send-only permission cannot be proven by reading mail. | Report transport, auth, permission and policy failures separately. Never claim SMTP login proves Send As or API consent proves submission. Offer reauthorization for rejected refresh grants; show admin/client restriction guidance. |
| Alias / delegation | Gmail send-as status when available; cached evidence labeled with age. Microsoft user-configured identity plus available evidence; no comprehensive Graph enumeration of Send As rights. | Known pending/unverified, configured evidence and unknown are distinct. Ask admin to confirm Send As/Send on Behalf, shared access and intended Sent settings. Missing lookup permission is unknown, not unauthorized. |
| Custom-domain DNS | User-selected owned From domain; SPF TXT and DMARC TXT lookups. DKIM queries only with provider/admin-supplied selectors; distinguish timeout, NXDOMAIN, absent record and malformed/multiple records. Record resolver, queried name, TTL and observation time. | DNS presence is not proof of DKIM signing, SPF pass, DMARC alignment or inbox placement. Do not guess selectors or prescribe a replacement SPF record; provide provider/domain-admin instructions to review signing and received authentication evidence. Consumer provider domains are provider-managed. |
| Result / sharing | Per-check UTC timestamp, route/mailbox identity, passed probe, failed, unknown, skipped or cancelled, evidence age and redacted error/request ID. Overall summary lists unresolved checks without a score. | TLS errors: correct host/certificate through established trust workflow. Disabled protocol: ask admin about an allowed route; never recommend weakening security defaults. Throttling: retry after stated time. Export only on user action; redact tokens, client secrets, message content and unnecessary addresses. |

Domain guidance: [Microsoft authentication overview](https://learn.microsoft.com/en-us/defender-office-365/email-authentication-about), [DKIM setup and signing](https://learn.microsoft.com/en-us/defender-office-365/email-authentication-dkim-configure). Received authentication headers require a separately authorized live message and a trusted receiving system; client-created Authentication-Results cannot prove anything.

## Future regression and authorized live checks

| Scenario | Required controlled fixture / invariant |
| --- | --- |
| OAuth expiry / revocation | Expired token refresh, concurrent parent/shared refresh, retained/rotated token, invalid_grant, partial consent, wrong-resource token; preserve draft and explain reauthorization without credential leakage. |
| Disabled protocols / policy | IMAP denied with SMTP or API available, SMTP denied with IMAP available, API policy denial and both protocols denied. Hybrid must report receive failure even when API sending could work. |
| Alias / delegation failure | Gmail pending/unknown lookup; Microsoft Send As denied, Send on Behalf identity, read-only shared access and alias policy. Preserve chosen From and explain missing rights without sending as another identity. |
| TLS failure | Invalid hostname, expired/untrusted certificate, missing STARTTLS and HTTPS validation failure; no plaintext fallback or unapproved trust bypass. |
| Throttling / rejection | SMTP 4xx/5xx at recipient/DATA; HTTP 403 policy/quota, 429 Retry-After and 5xx. Distinguish definite refusal from uncertain processing; bounded backoff for safe operations. |
| Ambiguous post-submission failure | Disconnect after SMTP DATA acceptance but before reply; HTTP server processes request then drops response. Keep unknown state across restart, no automatic resend/fallback; checking Sent is evidence, not an atomic idempotency guarantee. |
| Bcc-only / privacy | API-specific recipient mapping reaches intended Bcc addresses; received To/Cc/Bcc do not expose hidden recipients. Sender's Sent copy retains expected private metadata; no empty-envelope send. |
| International content / attachments | Unicode Subject/display names/body, IDN domains separately from non-ASCII local parts, long unbroken/folded subjects, multiple/inline attachments and size boundaries after base64/encryption. No silent truncation. |
| Encryption | PGP and S/MIME signed, encrypted and signed+encrypted messages; verify/decrypt received MIME with expected keys. Provider transformation must not break signatures; never downgrade. |
| Sent duplication / sync | SMTP copying enabled/disabled, custom route, Graph personal/shared endpoints with tenant copy settings, delayed Sent discovery, crash/restart and cursor replay. Expected copies by destination, no client-added duplicates. |

Optional live gate requires separate authorization specifying test accounts, From identities, recipients and cases: personal Gmail, Workspace with custom domain, Microsoft 365 normal/shared mailboxes, and Outlook.com for personal compatibility. Use disposable content and controlled recipients; record time, route, consent/policy evidence, provider response, bounce/delay, received From/Sender/Bcc privacy, MIME signature/decryption, attachment integrity and Sent counts/destinations. Ask the domain/tenant admin to confirm actual policy and DKIM signing; inspect trusted received SPF/DKIM/DMARC results and alignment. Record observed inbox/junk/quarantine at each recipient and time, without generalizing a small test to guaranteed placement. No automatic sends or configuration/DNS changes are authorized by this report.

Primary-source browsing checked linked API documentation on the review date; P1 retains the protocol/domain evidence and static findings. Direct diff review and documentation simplification found no further changes warranted; no code simplification applies. `git diff --check d579059bd5af1ca898c619b5abd02f4923139643 -- PLAN.md docs/validation/provider-transport-recommendations.md` passed; `git diff --exit-code d579059bd5af1ca898c619b5abd02f4923139643 -- archive frontend/wailsjs/runtime` was empty. A targeted Python evidence check passed the six acceptance sections, PD1–PD9 coverage, ten regression scenarios and current source-line bounds. These structural checks do not prove provider behavior. No application tests/builds, UI check, email, DNS or tenant changes were run in this research-only phase; no executable baseline result is claimed. Provider preservation of encrypted MIME, API Bcc behavior, aliases, tenant access, Sent destinations and actual delivery remain live validation gates.
