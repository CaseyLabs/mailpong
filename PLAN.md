# Provider implementation plan and deferred work

## Scope

Common provider correctness and safety work F1–F3c is complete for ordinary personal/business correspondence, aliases and shared mailboxes, using the [P1 audit](docs/validation/provider-deliverability-review.md) and [P2 recommendations](docs/validation/provider-transport-recommendations.md) as the requirements baseline. Live compatibility remains separately gated. The user selected full Gmail API and full delegated Microsoft Graph with optional existing-account migration on 2026-10-13. Implementation is authorized one milestone per project-next-milestone invocation.

Retain user-supplied desktop OAuth credentials, registered audiences, account IDs, drafts, queued mail, encrypted credential storage, legacy persisted identifiers, international message content and existing permitted routes. No dependency changes, provider registrations, tenant policies, DNS mutations or test emails are authorized. Do not weaken security defaults, certificate validation or encryption. No route promises delivery or inbox placement.

**Selected architecture:** full Gmail API sending/receiving for personal Gmail and Workspace; full delegated Microsoft Graph sending/receiving for Microsoft 365, including shared mailboxes. Outlook.com remains a separate compatibility target. Include explicit opt-in migration of existing accounts with preservation and rollback after backend parity verification. Existing accounts retain their configured routes until that migration; no automatic switch or transport fallback. Full compatibility is the target, subject to provider policies, permissions, feature parity and separately authorized live evidence, not a current claim.

G4/AI5 and D2 remain deferred; do not resume them automatically. Remaining provider findings stay in ISSUES.md until their relevant fixes are verified. Implement one milestone per invocation. F4a–F4e are done; F5 (split F5a–F5c, refined 2026-10-13) is next; later API milestones depend on their listed prerequisites and require focused acceptance refinement before implementation. Each includes documentation, independent acceptance, simplification and commit/push.

Preserve keyboard access; follow the skill's guarded/headless path and stop servers started for checks. Regenerate changed Wails bindings with `make generate` after stopping Mailven; revert unrelated runtime churn. Record route/time, provider acceptance, later bounce/delay and observed inbox/junk/quarantine without promising placement. Never send automatically or change external configuration.

### F4c — API submission clients

Backend-only, inert: add Gmail API and Graph submission clients behind a transport-neutral interface and journal integration, but do not switch any account route, add UI, or send to a live provider. Staged routes remain unread by app send paths. Base: `301c841`. Existing `smtp.SendMailTracked` callers (`app/compose.go`, `app/settings.go`) stay unchanged.

Acceptance:
1. A `submission`-level interface takes the already-built final MIME, envelope sender and recipients, and returns the same honest outcome vocabulary as `smtp.SubmissionResult` (not-submitted, rejected, accepted, unknown) with stage. Preflight rejects, without truncation or fallback: provider/route not `staged`/`active` with a matching grant, a missing `send` capability (`credentials.RequireMailAPICapability`), a From not in the account's verified identities (Gmail send-as cache) or, for Graph, a From that needs `.Shared` consent when not granted, and content over documented provider limits. Limits are recorded as documented constants with sources in Surprises, not probed.
2. Gmail client uses `users.messages.send` with the raw MIME (base64url) via the API access token from the isolated slot, refreshed only through the F4b locked snapshot refresh. Graph client uses the documented MIME `sendMail` form. Recipient mapping (To/Cc/Bcc) is derived from the envelope list, and fixtures prove Bcc recipients are not exposed in any header the client adds. Where provider Bcc/MIME handling is undocumented, record it as unverified rather than assume it.
3. Outcome honesty: 2xx = accepted (not delivery); 4xx definitive rejection classified via `oauth2.ClassifyMailAPIError` (reauthorize/policy/resource/other); 429/5xx and timeouts after the request body was sent = unknown, never retried or replayed, never falling back to SMTP; failures before any byte is sent = not-submitted. A durable unknown checkpoint is written before the request, using the existing `submission` journal (F2a), and a positive response is committed before local cleanup. Throttling `Retry-After` is surfaced as a backoff hint, not an automatic retry.
4. Auth failure handling: 401 triggers at most one locked snapshot refresh and a single re-attempt only when the first request provably was not accepted (rejected before send); `invalid_grant` marks the route for reauthorization via the F4b event and clears no protocol credentials. Fixtures prove no second send after an unknown outcome.
5. Local httptest fixtures (no external calls, no new dependencies, TLS validation unchanged) cover all above, plus international addresses/content, attachments near limit, signed/encrypted raw MIME passthrough byte-identical, and request cancellation. `docs/MAIL_APIS.md` and `docs/SENDING.md` document the clients, outcome mapping, journal use and the fact that nothing is activated; ISSUES.md records any confirmed unfixed findings.

Proof mapping: criteria 1–4 → `go test ./internal/submission ./internal/gmailapi ./internal/graphapi` (new package for Graph; Gmail sender may live in `internal/gmailapi`) and `go test ./app -run MailAPI`; criterion 5 → fixtures plus diff/documentation review. Final checks: `GOTOOLCHAIN=go1.26.8 go test ./internal/... ./app`, `GOTOOLCHAIN=go1.26.8 make test`, `PATH=/tmp/node-v24.21.0-linux-x64/bin:$PATH GOTOOLCHAIN=go1.26.8 make lint`, `git diff --check`. No frontend change, so no UI check.

### F4d — API receive/sync (refined 2026-10-13; split for independent verification)

Backend-only and inert: read-only mail ingestion for staged `google-mail-api`/`microsoft-mail-api` routes into disposable/local stores. No route activation, no UI, no write-back (flags, moves, deletes are F4e), no live provider calls; `app` sync schedulers must not read staged routes. Base: commit of F4c (`87ec22d`). Existing IMAP sync (`internal/sync`) stays unchanged except for reuse of its MIME parser/threading via a narrow exported seam.

Premises from the code: `message.Message` rows are keyed `(folder_id, uint32 uid)` with IMAP `UIDVALIDITY`/`UIDNEXT`/`HighestModSeq` on `folder.Folder`; threads come from `internal/sync/threading.go` (Message-ID/References); bodies parse from raw MIME. API IDs are opaque strings and Gmail messages carry many labels, so the IMAP key cannot be reused directly.

**F4d-1 — API identity mapping and sync-state storage.**
1. Migration (rerunnable, with rewind lines in `database_test.go`) adds an `api_message_refs` table (account_id, provider, remote_id, remote_thread_id, local message ID, remote container/label set JSON, remote version/etag) and `api_sync_state` (account_id, scope = mailbox/label/folder, opaque cursor, cursor kind, generation, updated_at). IMAP rows and columns are untouched; existing `uid` stays a local, per-folder monotonically assigned surrogate for API rows only, never sent to a provider.
2. Mapping rules are documented and fixture-proven: Gmail labels → Mailven folder types (INBOX/SENT/DRAFT/TRASH/SPAM/user labels; STARRED/UNREAD → flags; IMPORTANT/CATEGORY_* kept as metadata, not folders); a multi-label message yields one local row per mapped folder sharing one `api_message_refs` identity; Graph folders map by well-known name and `parentFolderId`, one row per message. Unknown/unmappable containers are kept as unmapped metadata, never dropped or guessed.
3. Cursor store: save, load, advance-after-commit and invalidate (generation bump). A cursor advances only in the same transaction that stores its page; crash fixtures prove no skipped or duplicated page.
Proof: `go test ./internal/database ./internal/account ./internal/message -run 'API|Migration'`.

**F4d-2 — Gmail receive.**
1. `internal/gmailapi` read client (access token from the isolated slot, locked-refresh/401-once policy reused from F4c; no redirects; no new dependencies): `labels.list`, `messages.list` (paged), `messages.get?format=raw` (base64url → byte-identical MIME), `history.list` with `historyTypes` for messageAdded/Deleted/labelAdded/labelRemoved, and `users.getProfile` for the starting `historyId`. Capability gate: `read` via `credentials.RequireMailAPICapability`.
2. Initial sync pages `messages.list` per bounded window, records the profile `historyId` captured *before* listing, and fetches raw MIME with bounded concurrency honoring `Retry-After`/429 backoff (no unbounded retry; surfaced as a hint). Incremental sync applies history in order; label add/remove updates the per-folder rows and flags; deletes remove rows and refs.
3. Reset recovery: a history `404` (expired/invalid `historyId`) marks the cursor invalid, bumps the generation and runs a full reconcile that diffs remote IDs against local refs (adds missing, removes vanished, preserves local-only state such as bodies already stored and read/flag state pending F4e write-back); local data is never wiped on failure. A mid-reconcile failure leaves the old data and an unreconciled marker.
4. Ingestion reuses the existing parser so S/MIME and PGP raw bodies, attachments, international headers/charsets and threading behave as IMAP rows (same fixtures: signed, encrypted, non-UTF-8 charset, IDN addresses). Gmail `threadId` is stored as `remote_thread_id` but local `thread_id` still derives from headers, so IMAP↔API migration (F5) keeps threads stable.
5. `invalid_grant`/403 policy errors route through `ClassifyMailAPIError` and the F4b reauthorization event; rate-limit 403/429 pause sync without clearing credentials.
Proof: `go test ./internal/gmailapi ./internal/sync -run 'Gmail|API'` against `httptest` servers only (no external calls).

**F4d-3 — Microsoft Graph receive.**
1. `internal/graphapi` read client: `mailFolders` (+ `childFolders`), per-folder `messages/delta` with `Prefer: IdType="ImmutableId"` so renames/moves keep identity, `messages/{id}/$value` for raw MIME, and paged `@odata.nextLink`/`@odata.deltaLink`. Requests use the mailbox in the route (own, or `users/{shared}` only with the `.Shared` grant). Capability gate: `read`.
2. Initial and incremental delta per folder with the cursor store; `@removed` entries delete rows; a move appears as remove+add under the same immutable ID and updates the ref instead of duplicating the message.
3. Reset recovery: `410 Gone` (`syncStateNotFound`/`resyncRequired`) invalidates only that folder's cursor and runs the same diff-reconcile as Gmail; a deleted/renamed folder is reconciled, not left stale.
4. Same ingestion, error classification, throttling (`Retry-After`, 429/503 pause, no replay) and no-credential-clearing rules as Gmail; shared mailbox without consent fails explicitly.
Proof: `go test ./internal/graphapi ./internal/sync -run 'Reader|Graph|API'`.

**Milestone-wide acceptance:** documented provider limits and endpoints (page sizes, history retention, delta behaviour) cite sources in Surprises and are recorded as constants, not probed; `docs/MAIL_APIS.md` gains "API receive and sync (inert)" covering mapping, cursors, reset recovery and limits; ISSUES.md records any confirmed unfixed findings; fixtures cover cancellation and crash-between-page-and-cursor. Run F4d-1, F4d-2, F4d-3 as separate invocations, each with the final checks `GOTOOLCHAIN=go1.26.8 go test ./internal/... ./app`, `GOTOOLCHAIN=go1.26.8 make test`, `PATH=/tmp/node-v24.21.0-linux-x64/bin:$PATH GOTOOLCHAIN=go1.26.8 make lint`, `git diff --check`. No frontend change, so no UI check.

### F4e — API actions and route activation (refined 2026-10-13; split for independent verification)

Premises from the code: user actions in `app/actions.go` update the local row first, then write to IMAP directly (`withIMAPRetry`; Gmail trash/label paths special-cased); there is no persisted action queue, and `app/sync.go` schedules IMAP folder sync only. API rows (F4d) have a local surrogate `uid`, so IMAP calls must never receive it. Staged routes (F4b) change nothing until F4e-3. No live provider calls; `httptest` only.

**F4e-1 — API write clients (inert).**
1. `internal/gmailapi` write calls: `messages.modify` (add/remove label IDs, covering read/unread, star, move between labels, archive), `messages.trash`/`untrash`, batch variants within the 1000-ID limit; no permanent delete (the ordinary profile excludes it). `internal/graphapi`: `PATCH messages/{id}` (`isRead`, `flag`) and `POST messages/{id}/move` (returns the new immutable ID); trash is a move to Deleted Items; permanent delete is not offered. Capability gate: `write` via `RequireMailAPICapability` (+ shared flag); a refused grant sends no request.
2. Outcomes use the F4c vocabulary: applied / rejected (4xx, including 404 gone) / unknown (transport failure or ambiguous 5xx) / reauthorize/policy. Unknown never auto-replays a non-idempotent move; idempotent label/flag sets may be retried by the queue after verification (`messages.get` minimal / Graph GET).
3. 401-once, no redirects, `Retry-After` honored (cap 60 s), 3 rate-limit retries, no new dependencies; a Graph move result updates the ref's remote ID/container atomically with the local row.
Proof: `go test ./internal/gmailapi ./internal/graphapi -run 'Write|Modify|Move'`.

**F4e-2 — Local-first action queue and routing.**
1. Migration (rerunnable, with rewind lines) adds `api_pending_actions` (id, account_id, op, local message IDs, remote IDs, payload JSON, status pending/in-flight/applied/rejected/unknown, attempts, next_attempt_at, error, created_at). Local state changes in one transaction with the queue row, so a crash cannot lose or duplicate an action and the UI never waits on the network.
2. A per-account worker applies actions in order, coalesces opposite flag toggles, marks a stuck in-flight row `unknown` after restart and verifies remote state before any re-send, and uses persisted exponential backoff (5 s to 5 min) on throttling. A rejected action reverts the local row to remote state and emits `sync:error`; an unknown action is surfaced for review, never silently replayed or reverted.
3. F4d reconciliation must not overwrite a row with a pending action; pending local flags/folder win until the action resolves.
4. `app/actions.go` routes through an `actionBackend` seam chosen per account: IMAP (default, behavior and tests unchanged) or API when the route is **active**. Cross-account and undo paths work through the seam. Operations the API profile cannot do (permanent delete, cross-route copy) fail explicitly, never via IMAP fallback.
Proof: `go test ./app ./internal/message ./internal/database -run 'APIAction|Queue|Migration'` plus unchanged IMAP action tests in `./app`.

**F4e-3 — Route activation (opt-in, per account, reversible).**
1. `ActivateMailAPIRoute`/`DeactivateMailAPIRoute`: activation only from a staged route whose grant passes read/write/send gates, with no IMAP sync or queue action in flight. It never deletes IMAP data, credentials, drafts or queued mail, and starts with one API reconcile; failure leaves the account on IMAP.
2. While active: the scheduler runs `GmailSync`/`GraphSync` instead of IMAP folder sync for that account, submission uses the F4c API sender, and no automatic IMAP/SMTP fallback happens on any error. Deactivation (and `ClearMailAPIRoute`) returns to IMAP; API rows are kept until F5 decides their fate, hidden from IMAP views, never mixed in.
3. F4b reauthorization events pause the account's API sync and queue without clearing local data; existing sync status/error events are reused.
4. Backend only, no UI; Wails bindings regenerated for new methods. Non-staged accounts behave identically to today.
Proof: `go test ./app -run 'MailAPIRoute|Activation|APISync'`; IMAP scheduler tests unchanged.

**Milestone-wide acceptance:** `docs/MAIL_APIS.md` gains "API actions and activation"; Surprises cite provider limits (batch sizes, move semantics, label limits) as constants; ISSUES.md records confirmed unfixed findings; fixtures cover crash between local commit and queue write, restart with in-flight actions, 404/410 on actions, throttling, cancellation and deactivation mid-queue. ### F5 — Opt-in migration of existing accounts (refined 2026-10-13; split for independent verification)

Premises from the code: F4e-3 activation already swaps hidden folder rows (`folder.Store.SwapHidden`, `RowsIMAP`/`RowsAPI`), keeps API rows (`api_message_refs`/`api_message_rows`, surrogate `uid`) and IMAP rows side by side, and returns to IMAP on deactivation; local `thread_id` derives from headers, so threads survive a route change. Activation does not yet correlate API rows with existing IMAP rows, so activating an account with synced mail currently shows a second full copy. IMAP-direct body/attachment fetches still receive surrogate UIDs (MA5), shared-mailbox routes cannot activate (MA4) and cross-account/undo API moves fail explicitly (MA3). Gmail permanent delete stays excluded from the ordinary profile. No live provider calls; `httptest` and disposable data only. Live migration of a real account needs separate authorization (accounts, cases) and is not closed by fixtures.

**F5a — API read-path parity and pre-migration blockers (backend).**
1. Route `FetchMessageBody`, attachment listing/download, raw source and remote-image/crypto paths for API-routed accounts through the stored raw MIME or the API raw get (capability gate `read`), never IMAP with a surrogate UID (MA5). Fixtures: signed, encrypted, non-UTF-8, attachment, offline (cached) and 404-gone message.
2. Settle MA3: decide and implement either cross-account move as copy-then-delete through the sender/queue or keep the explicit error with user-facing wording; record the decision. API undo follows the same decision.
3. Fix CD1 (draft saved under a different selected account keeps the old `AccountID` while encryption uses the selected one) so draft ownership is unambiguous before migration. Gmail permanent delete: keep excluded; record that offering it needs a separate scope request and UX, deferred.
4. Store the shared-mailbox address with the route (MA4) only if cheap; otherwise leave shared routes unmigratable with an explicit reason and keep MA4 open.
Proof: `go test ./app ./internal/message -run 'APIBody|APIAttachment|APIMove|Draft'`; unchanged IMAP tests.

**F5b — Migration engine with snapshot, correlation and rollback (backend).**
1. `PlanMailAPIMigration` is read-only: reports route, grant gates, row counts, drafts, queued/outbox items, pending actions and blockers (in-flight sync, unknown actions or submissions, unresolved reauth). `MigrateMailAPIAccount` refuses on any blocker.
2. Snapshot before any change: consistent SQLite copy (`VACUUM INTO`) of the database plus the route row to a user-data directory, owner-only, with a manifest (version, account ID, counts, time). The snapshot never contains credentials beyond what the database already stores; no token is copied elsewhere.
3. Preserve account ID, credentials, identities, drafts, outbox/queued mail, rules and contacts. Correlate each API ref with an existing IMAP row by `Message-ID` plus folder/date and carry local state (read, flags, cached body, thread, labels) onto the API link instead of creating a duplicate; uncorrelated messages are added once. Re-running after interruption is idempotent (no duplicates, no lost rows), proven by killing the migration between each step in fixtures.
4. Rollback (`RollbackMailAPIMigration`) restores IMAP route state and visible folders, replays nothing to the provider automatically, and runs an IMAP reconcile; actions queued or applied on the API side after migration are reported, not silently dropped. Restoring the full snapshot is a separate explicit user choice that warns about losing later local changes.
5. Failure at any step leaves the account on IMAP with data intact. No automatic IMAP/SMTP or API fallback after migration.
Proof: `go test ./app ./internal/apimigrate ./internal/message ./internal/folder -run 'Migrat|Rollback|Correlat|Snapshot'`; IMAP-only accounts unchanged.

**F5c — Opt-in migration UI and documentation.**
1. Settings per-account flow: explain route, scopes and limits (no promise of delivery or placement), consent, plan/blockers view, confirm, progress, cancel before commit, rollback; English strings only; keyboard accessible; native selects with accessible names; status via existing sync events.
2. Account list/Mail view show the active route; reauth and policy errors reuse existing error surfaces.
3. Docs: MAIL_APIS.md "Migration and rollback" plus user-guide and SENDING.md updates; rollout gates restated with the unverified live items (Bcc privacy MA1, shared mailboxes, size limits).
Proof: `cd frontend && npm run lint && npm run check && npm run build`, run-mailven guarded/headless UI check with fakes (Mail view Accounts expanded and collapsed, migration and rollback paths), `make generate` bindings after stopping Mailven.

## Surprises & Discoveries
