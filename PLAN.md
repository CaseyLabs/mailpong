## Surprises & Discoveries

- 2026-10-13 F5b: API refs carry Message-IDs without angle brackets while IMAP keeps them, and SQLite `strftime` returns NULL for the driver's stored dates, so correlation normalises the ID and parses dates in Go. API rows already hold a fetched body, so the IMAP cached body is only carried when the API row has none. Snapshot restore is deferred.

- F4e-3: hidden folder rows need `List`, `GetByPath` and `ListSubscribed` filters, and `emitSyncError`/`emitFolderSynced` called the Wails runtime directly, which fatals without a UI context in tests; they now use the `eventsEmit` seam. No new provider limits were introduced (batch size 1000, Retry-After cap 60 s and 3 retries are in F4e-1; delta/history page sizes in F4d).

- F4e-2: a Graph delta `@removed` for the old ID during an in-flight move can delete the local rows; the next sync restores them under the new ID, so it self-heals. Gmail user labels cannot be mapped to IDs offline: a move into or out of one needs `labels.list` (15 s timeout), and fails explicitly when offline. `Worker.Drain` skips an account already draining, so a kick during a drain is re-run by `kickAPIActions` (dirty flag). Gmail untrash restores the message without folder labels (it then lives in All Mail locally until the next sync corrects it).

- F4e-1 limits (constants in `internal/gmailapi/write.go` and `internal/apiwrite`; not probed): `messages.batchModify` accepts at most 1000 IDs (developers.google.com/gmail/api/reference/rest/v1/users.messages/batchModify); Gmail rate limits arrive as 429 or 403 `rateLimitExceeded`; Graph `move` returns a message with a new ID, and `deleteditems` is a well-known destination name (learn.microsoft.com/graph/api/message-move). Graph `Prefer: IdType="ImmutableId"` keeps IDs stable across folder moves where supported; the move response ID is still re-keyed locally.
- F4d-3 limits (constants in `internal/graphapi/read.go` and `internal/sync/graphapi.go`; not probed): message delta supports `Prefer: odata.maxpagesize` and returns `@odata.nextLink`/`@odata.deltaLink`, one delta per folder (learn.microsoft.com/en-us/graph/api/message-delta, /graph/delta-query-messages); `Prefer: IdType="ImmutableId"` keeps IDs stable across moves (learn.microsoft.com/en-us/graph/outlook-immutable-id); Outlook allows 4 concurrent requests per app and mailbox and throttles with 429 plus `Retry-After` (learn.microsoft.com/en-us/graph/throttling-limits#outlook-service-limits), hence 4 workers. A moved message appears as `@removed` in the source folder's delta, so removals are verified with `GET /messages/{id}` before deleting. Unverified assumptions: delta page size 50, folder page size 100, the 64 MiB raw-message cap, and 400 with "syncState" being treated as an expired token (documented token failures are 410).
- F4d-2 limits (constants in `internal/gmailapi/read.go` and `internal/sync/gmailapi.go`; not probed): `messages.list` and `history.list` maxResults ceiling 500 (developers.google.com/gmail/api/reference/rest/v1/users.messages/list, .../users.history/list); history records are "typically available for at least one week, often much longer" and an expired startHistoryId returns 404 (developers.google.com/gmail/api/guides/sync); a rate-limit error may arrive as HTTP 403 or 429 (developers.google.com/gmail/api/guides/handle-errors); per-user quota 250 units/s with `messages.get` costing 5 units (developers.google.com/gmail/api/reference/quota), hence 4 concurrent fetches. `history.list` can return a message in several records and history may list a deleted message as added, so the driver aggregates net state per message.
- F4d-1: independent acceptance found a new message listing one folder twice would create duplicate rows; `CommitAPIPage` now rejects it. `CommitAPIPage` uses a deferred transaction (read-then-write); SQLite busy handling under concurrent writers is unverified. `internal/extensions/store.go` is already gofmt-unclean on this branch (not touched).

- F4b: `UpdateOAuthTokensForClientConfig` never clears a refresh token, so rejected API grants need the dedicated clear method. Microsoft AADSTS policy codes in an `invalid_grant` description classify as policy, though the token is still cleared and the event emitted. Generated `models.ts` blank lines carry tabs in the committed file; apply only real changes (`git diff -w` patch) instead of stripping them.

- F4a: current Gmail sendAs.list accepts gmail.modify, so the profile needs no extra gmail.settings.basic scope. Graph Shared delegated grants also cover the user's own mailbox; capability gates accept that documented superset while keeping own-only grants insufficient for another mailbox. Sources are linked in docs/MAIL_APIS.md.

- F3c: secure refresh is optional here and deliberately not invoked: existing refresh locks have no caller deadline, and refresh rejection emits reauthorization events. Read the linked owner's stored grant; near-expiry credentials skip auth with normal-refresh/explicit-reauthorization guidance. Do not claim login proves sending rights.
- F3c: use native/Flatpak save dialogs for desktop export; snapshot redacted results before opening the dialog without holding the run mutex. Free-form server errors can echo credentials, so discard them at collection instead of attempting string replacement later. Opaque custom grant metadata is redacted.
- F3c: wire TXT queries preserve TTL and NXDOMAIN/NODATA distinctions; portable system-resolver fallback explicitly marks unavailable metadata. DNS policy checks are structural, never SPF include evaluation, signing, alignment or delivery evidence. CNAME-only unresolved responses stay unknown. Guarded UI required explicit accessible names for native selects, and reports label their snapshotted mailbox/From independently of later input edits.

Persistent OS advisory lock files now coordinate refresh/reauthorization across those processes; never unlink an active lock file. Missing/rejected refresh material must keep grant metadata visible for reauthorization.

## Decision Log

- API sync callers must serialize runs per account: `GmailSync.Run` has no internal mutex. The production scheduler uses `app/api_route.go` `runAPISync` with the per-account lock, wired through `app/background.go`; future callers must preserve this invariant.

- 2026-10-13 F5b: snapshot restore remains unimplemented after F5c; rollback is route-level only (ISSUES.md F5b-1). Ambiguous correlations stay uncorrelated rather than guessed.

- 2026-10-13 F4e-3: folder swap (user-approved): IMAP and API folder rows coexist; the inactive set is hidden by `hidden:<tag>:<type>` type and a path prefix, swapped in one transaction. Activation sets the route active first (stops new IMAP syncs), then checks for a running IMAP sync and for in-flight/unknown actions (pending are allowed), then swaps and reconciles once; any failure reverts. Shared routes cannot be activated (Graph shared address unknown). Paused = reauth flag or a grant failing the gates; paused sync returns `errAPIPaused` with no IMAP fallback. API sends save no local Sent copy (the provider files it). Re-consent keeps an active route and rejects route/shared changes while active.

- 2026-10-13 F4e-2: one queue row per remote message (siblings follow flags); flags coalesce, moves use the clash-aware row move. Gmail moves are label changes plus the trash verbs; Graph moves re-key queued actions inside `ApplyAPIMove`. Receive sync skips refs with open actions (removals still apply). In-flight becomes unknown on restart and unknown is verified before any re-send; unverifiable stays unknown and is surfaced. Flags use single `Modify` calls rather than `BatchModify` (one queue row per message). `apiRouted` requires route state `active` (`account.MailRouteStateActive`); staged routes remain unused by production transport. The seam is `apiRouted` branches in `actions.go` rather than an `actionBackend` interface, since IMAP code stays untouched. Shared-mailbox routes fail the remote factory until shared actions are supported; API moves skip undo.

- 2026-10-13 F4e-1: one shared `internal/apiwrite` transport keeps outcomes and retries identical for both providers. Only 429 (or a 403 rate-limit body) is retried (3 times, `Retry-After` capped at 60 s); 5xx, redirects and post-write transport failures are unknown and never replayed. No batch trash/untrash variant: Gmail has no endpoint and `batchModify` with `TRASH` is unverified, so only `BatchModify` (1000 per call) exists and the queue loops single `Trash` calls (deviation from the "batch variants" wording). `ApplyAPIMove` re-keys by insert/repoint/delete because `api_message_rows` has no `ON UPDATE CASCADE`.
- 2026-10-13 F4d-3: shared receive plumbing (folder cache, backoff, fan-out, raw parse) moved to `internal/sync/apicommon.go` and the Gmail driver now uses it; the read clients stay separate because their error and paging shapes differ. A Graph reconcile is a fresh delta enumeration plus a per-message GET of local IDs it did not list, so a message moved to another mapped folder keeps its ref instead of being deleted and refetched. The folder map ID->path is stored under cursor scope `folders` to detect renames, which reconcile that folder only. Graph `conversationId` is stored as `remote_thread_id` only.
- 2026-10-13 F4d-2: crypto raw bodies and attachments ride in the page transaction (`APIRowExtras`) instead of a follow-up write, so no crash window leaves a body without them. Label-only changes use `APIRow.FlagsOnly` so `Message.Get` data (which omits references) is never written back. A reconcile re-checks known messages by `minimal` GET against the stored historyId rather than assuming equality, costing one request per message on the rare reset path.
- 2026-10-13 F4d-1: identity and cursor storage live in `internal/message` (one transaction needs messages, refs and cursor together); a separate `api_message_rows` link table carries the local-row side of the identity so a multi-label message has one `api_message_refs` row. Surrogate UIDs come from `folders.uid_next`. Ingestion creates mapped folders.

- 2026-10-13 F4c: deviation from criterion 2 wording: Bcc cannot be omitted from headers because the APIs derive recipients from them; the client adds only a `Bcc:` naming hidden recipients and records provider stripping as unverified. 429 is unknown (not retried), per the outcome spec. The only retry is one 401 re-attempt after a locked forced refresh; the API token source rejects a stale token by comparing against the rejected value.

This authorizes local implementation, not live provider access, mail, registrations or tenant changes. Separate API grant slots preserve protocol credentials during staging. Gmail ordinary API profile excludes immediate permanent deletion; adding it requires separate permission/UX work.
